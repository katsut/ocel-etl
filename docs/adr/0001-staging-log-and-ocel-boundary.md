# ADR 0001: StagingLog を中間表現とし、Ocel への変換を検証ゲートにする

- **ステータス:** Accepted
- **日付:** 2026-07-01
- **スコープ:** ocel-etl（このリポジトリ内の決定）
- **関連:** ターゲット型 `ocel_core::Ocel` の設計は ocel-rs の [ADR 0001: OCEL ネイティブ core](https://github.com/katsut/ocel-rs/blob/main/docs/adr/0001-ocel-native-core.md)

---

## コンテキスト

ocel-etl は多様なソース（Issue Tracker 等）から OCEL 2.0 を生成する汎用 ETL エンジン。ターゲット型は `ocel_core::Ocel`（厳格・検証済み・OCEL 2.0 ネイティブ）。しかし抽出・変換の途中では、その厳格さが成り立たない。

## 決定

1. **ETL の作業表現は `StagingLog`**（緩い・宙吊り参照OK・成長するスキーマを許容）とする。`ocel_core::Ocel` を作業バッファに使い回さない。
2. **`ocel_core::Ocel` への変換は `impl TryFrom<StagingLog> for Ocel`＝検証ゲート**（宙吊り参照の解決確認・スキーマ確定・動的属性の時系列整列・仕様準拠チェック）。両者の唯一の接点。
3. **provenance（`rule` / `llm` 等の出自）は属性として境界を越えて保持**する。ETL 内部に閉じ込めず、生成したログでも「どう作られたか」を追えるようにする。

## 根拠（なぜ厳格な OCEL を作業バッファにしないか）

破綻の主犯は**パフォーマンスではなく、OCEL 2.0 が前提とする「完全性・不変条件・順序」**。抽出途中はこれが成り立たない:

- **① 宙吊り参照:** API のページングにより、イベントが未取得のオブジェクトを参照する順序が普通に起きる。`Ocel` の E2O は「存在するオブジェクトを指す」のが不変条件のため、途中状態を表現できない。
- **② 後から生えるスキーマ:** OCEL 2.0 は型と属性を先に宣言する。抽出中は属性が後のページで判明する。最終スキーマの確定には蓄積が要る。
- **③ プレ OCEL 状態:** ソースに Case ID が無い場合は相関（correlation）が要る。相関前・フィルタ前・抽象化前のデータは「まだ妥当な OCEL ではない」。
- **④（副次）パフォーマンス:** OCEL の自然な in-memory 形（オブジェクトグラフ）は大量構築・ストリーミングに不向き。

①②③が主因、④が後押し。これらはすべて `StagingLog` で吸収し、`TryFrom` ゲートを通った瞬間に妥当な `Ocel` だけが core に入る。

## 結果

- ETL のカオスが core に漏れない。検証が `TryFrom` の1箇所に集約される。
- `StagingLog` という別モデルの設計・保守コストが増える（許容）。
- ソース（Backlog 等）の意味論は OCEL 2.0 と好相性だが、実装難度が高い部分（配管・非構造データ）を ETL 側に隔離できる。

## 却下した案

- **厳格な `Ocel` を ETL の作業バッファに流用** → ①宙吊り参照・②成長スキーマ・③プレ OCEL 状態を表現できず破綻する。
